### D-02：错误处理流程缺失

**原问题**：没有错误码定义、错误传递机制、用户友好消息

**开发者修复声明**：补充错误码定义、异常传递机制

**验证结果**：✅ **修复质量良好**

**证据**（系统设计方案 6.1 节）：

1. **错误码定义完整**：
   | 错误码 | 类型 | 说明 |
   |-------|------|------|
   | E001 | 参数错误 | 缺少必填参数或参数格式错误 |
   | E002 | 数据不存在 | 配方/价格/客户不存在 |
   | E003 | 权限错误 | 用户无权访问该数据 |
   | E004 | 业务错误 | 成分比例不等于 100% 等 |
   | E005 | 系统错误 | 数据库连接失败等 |

2. **错误传递机制清晰**：
   ```python
   class ServiceResult:
       success: bool
       data: Optional[Dict]
       error_code: Optional[str]
       error_message: Optional[str]
   ```

3. **用户友好消息转换**：Harness 层根据错误码生成用户可理解的消息

**评估**：
- ✅ 错误码覆盖核心场景（参数、数据、权限、业务、系统）
- ✅ 采用结构化错误对象（ServiceResult），而非异常抛出
- ✅ 分离了技术错误码和用户消息
- ⚠️ **改进建议**：缺少 E006（乐观锁冲突）的正式定义（代码示例中出现但未在错误码表中）

### D-03：并发控制未说明

**原问题**：多用户同时修改同一数据时无控制机制

**开发者修复声明**：乐观锁设计（version 字段）

**验证结果**：✅ **修复完整**

**证据**（系统设计方案 6.2 节）：

1. **Schema 设计**：
   ```sql
   ALTER TABLE formulas ADD COLUMN version INTEGER DEFAULT 1;
   ```

2. **更新语句**：
   ```sql
   UPDATE formulas 
   SET name = ?, stage_type = ?, version = version + 1
   WHERE id = ? AND owner_open_id = ? AND version = ?;
   ```

3. **应用层处理**：
   ```python
   if result.rowcount == 0:
       return ServiceResult(
           success=False,
           error_code="E006",
           error_message="数据已被其他用户修改，请刷新后重试"
       )
   ```

**评估**：
- ✅ 乐观锁三要素完整（version 字段、WHERE 条件检查、行号判断）
- ✅ 用户提示友好（"数据已被其他用户修改"）
- ✅ 与 owner_open_id 隔离机制结合正确
- ⚠️ **改进建议**：应明确说明 version 字段需要添加到哪些表（formulas、customers、ingredient_prices 等所有可更新表）

### D-04：Session State 持久化策略不明确

**原问题**：会话状态存在哪里？内存还是数据库？过期策略？

**开发者修复声明**：内存 + 可选数据库策略

**验证结果**：✅ **修复合理**

**证据**（系统设计方案 6.3 节）：

1. **双层存储架构**：
   ```python
   class SessionStateManager:
       def __init__(self, db_pool: Optional[DatabasePool] = None):
           self.memory_store = {}  # 内存缓存
           self.db_pool = db_pool  # 可选数据库持久化
           self.ttl = 3600  # 1 小时过期
   ```

2. **查询策略**：内存 → 数据库 → 新建

3. **过期清理**：`cleanup_expired()` 方法定期清理

**评估**：
- ✅ 默认内存存储（性能优先）
- ✅ 可选数据库持久化（支持分布式部署）
- ✅ TTL 机制防止内存泄漏
- ✅ 设计符合"最小可用"原则（v1.7 可先用内存版）

## 4. 工作量评估

### 4.1 调整对比

| Phase | 原估算 | 调整后 | 增量 | 调整理由 |
|-------|-------|--------|------|---------|
| Phase 1 | 4h | 4h | 0h | 无变化 |
| Phase 2 | 8h | 10h | +2h | 增加 Service 测试 |
| Phase 3 | 4h | 4h | 0h | 无变化 |
| Phase 4 | 4h | 6h | +2h | 依赖注入改造 |
| Phase 5 | 4h | 6h | +2h | 对话逻辑 |
| Phase 6 | 4h | 4h | 0h | 无变化 |
| Phase 7 | 2h | 2h | 0h | 无变化 |
| **合计** | **30h** | **36h** | **+6h** | **+20% 缓冲** |

### 4.2 评估意见

**✅ 调整合理**

理由：
1. **Phase 2（+2h）**：Service 层是核心业务逻辑，增加测试时间合理。每个 Service 需要测试：
   - 基本 CRUD
   - 多用户隔离
   - 私有/公共回退
   - 边界条件

2. **Phase 4（+2h）**：技能改造涉及依赖注入，需要：
   - 修改技能初始化逻辑
   - 更新技能工厂
   - 回归测试（确保改造不影响现有功能）

3. **Phase 5（+2h）**：私有数据功能的对话逻辑比预期复杂：
   - 多轮对话状态管理
   - 参数提取和验证
   - 错误处理和用户提示

**风险**：
- Phase 2 的 10h 可能仍然偏紧（5 个 Service × 2h/Service = 10h，刚好够）
- Phase 6 的测试时间未增加，但测试场景显著增多（多用户、回退、并发）

**建议**：如果 Phase 2 延期，考虑从 Phase 6 借调时间（测试可以分阶段进行）。

## 5. 新发现问题

### N-01：错误码 E006 未正式定义

**问题描述**：
- 6.2 节并发控制代码示例中使用了 `error_code="E006"`
- 但 6.1 节错误码定义表中只有 E001~E005

**影响**：
- 开发人员可能遗漏 E006 的定义
- 错误码不连续，后续维护困惑

**建议修复**：
在 6.1 节错误码定义表中补充：
| E006 | 并发冲突 | 数据已被其他用户修改 |

---

### N-02：version 字段应用范围不明确

**问题描述**：
- 6.2 节只展示了 `formulas` 表添加 version 字段的示例
- 但 `customers`、`ingredient_prices` 等表同样需要乐观锁

**影响**：
- 开发人员可能只给 formulas 表添加 version
- 其他表的并发修改无保护

**建议修复**：
在 6.2 节明确说明：
> 以下所有可更新业务表均需添加 version 字段：`formulas`、`customers`、`ingredient_prices`、`quotes`

---

### N-03：日志保留策略缺失

**问题描述**：
- 6.4 节定义了日志格式和类型
- 但未说明日志存储位置、保留期限、清理策略

**影响**：
- 日志可能无限增长，占用磁盘空间
- 审计合规性要求可能不满足（如需要保留 6 个月）

**建议修复**：
在 6.4 节补充：
```markdown
#### 日志存储策略
- **存储位置**：`logs/audit.log`（按天轮转）
- **保留期限**：操作日志 30 天，审计日志 180 天
- **清理策略**：每日凌晨 2 点清理过期日志
```
